# AI 활용 회고 메모

## 1. AI를 처음에 어떤 용도로 사용했는가?

처음에는 아이디어 정리, MVP 범위 설정, FastAPI 코드 초안, Docker Compose와 Kubernetes 설정 초안, Prometheus와 Jaeger 연동 방식 정리, 발표용 문서와 데모 시나리오 작성에 AI를 사용했다.

특히 "LLM 서비스 운영자가 실제로 무엇을 보고 싶어 할까?"라는 질문을 비용, 토큰, latency, 병목, 실패, 알림 같은 운영 질문으로 정리하는 데 도움을 받았다.

## 2. AI가 제안했지만 그대로 따르지 않은 방향

AI가 외부 LLM API를 중심으로 구성하는 방향을 제안한 적이 있었지만 그대로 따르지 않았다. 외부 API는 비용, 쿼터, 네트워크 상태에 따라 시연이 불안정해질 수 있다고 판단했기 때문이다.

또한 로그인, 회원 기능, 조직별 권한 관리, 복잡한 멀티테넌시, 과한 분석 기능 등은 프로젝트의 핵심보다 범위를 키우는 요소라고 보고 제외했다.

## 3. 핵심이 아니라고 판단해서 뺀 기능

사용자 로그인, 관리자 권한 관리, 장기 로그 저장소, 실제 과금 시스템, 여러 외부 LLM 제공자 비교 기능은 MVP에서 제외했다.

이번 프로젝트의 핵심은 LLM 답변 품질을 평가하는 것이 아니라, LLM 서비스가 운영될 때 비용, 속도, 실패, 병목을 관측하는 것이라고 판단했다. 따라서 교수님이 말한 "마이너한 내용은 빼라"는 기준에 맞춰 관측성과 시연 가능성에 직접 연결되지 않는 기능은 줄였다.

## 4. 처음 기획에서 최종 결과물까지 가장 크게 바뀐 방향

처음에는 단순히 LLM 호출을 관측하는 수준으로 생각했지만, 최종 결과물은 샘플 챗봇, 운영자 대시보드, Prometheus metric, Jaeger trace, 알림까지 포함한 관측성 MVP로 확장됐다.

즉, 단순 LLM 관측 실험에서 실제 운영자가 볼 수 있는 데모 서비스 형태로 방향이 바뀌었다.

## 5. SLM 도입을 결정한 이유

SLM을 사용한 이유는 단순히 비용 절감 때문만은 아니다.

로컬에서 반복 시연할 수 있고, 외부 API 장애나 쿼터 문제를 피할 수 있으며, 팀원들이 같은 환경에서 테스트할 수 있다는 점이 중요했다. 발표 환경에서도 외부 서비스 상태에 덜 의존할 수 있기 때문에 안정적인 데모가 가능하다고 판단했다.

## 6. Discord 알림을 붙일 때 상상한 운영 상황

운영자가 대시보드를 계속 보고 있지 않아도 지연, 에러율 증가, 토큰 사용량 증가 같은 이상 신호를 받을 수 있는 상황을 상상했다.

실제 운영에서는 문제가 생긴 뒤 직접 대시보드를 열어 찾는 것보다, 먼저 알림을 받고 해당 request_id나 trace_id를 기준으로 원인을 추적하는 흐름이 더 자연스럽다고 봤다.

## 7. request_id / trace_id / retrieve-llm_call-postprocess 구조를 정한 이유

request_id와 trace_id는 한 요청을 처음부터 끝까지 추적하기 위해 넣었다.

요청 내부 단계를 retrieve, llm_call, postprocess로 나눈 이유는 단순히 "응답이 느리다"라고 보는 것이 아니라 어느 단계가 느린지 구분하기 위해서다. 예를 들어 retrieve가 느리면 RAG 검색 문제이고, llm_call이 느리면 모델 생성 단계가 병목이라고 설명할 수 있다.

Jaeger에서는 이 구조가 span으로 보이기 때문에 발표 시에도 병목 단계를 시각적으로 설명하기 좋았다.

## 8. 5개 시나리오를 정한 이유

normal, slow_retrieve, slow_llm, high_token, error 시나리오는 실제 LLM 서비스 운영에서 자주 발생할 수 있는 상황을 대표하도록 정했다.

normal은 정상 요청, slow_retrieve는 검색 단계 병목, slow_llm은 모델 생성 병목, high_token은 토큰 증가와 비용 증가, error는 실패 요청 추적을 보여주기 위한 것이다.

동시에 발표 시연에서 짧은 시간 안에 정상, 지연, 비용 증가, 실패 상황을 모두 보여주기 위한 데모 목적도 있었다.

## 9. 프로젝트 중간에 가장 막혔던 문제

중간에 가장 어려웠던 부분은 Ollama 로컬 모델 실행, Docker/Kubernetes 포트 연결, Jaeger trace 연결, Prometheus metric 수집, 대시보드에서 trace와 metric을 연결하는 부분이었다.

특히 사용자가 요청을 하나 보냈을 때, Chat UI와 운영자 대시보드와 Jaeger에서 같은 요청으로 이어져 보이게 만드는 것이 중요했다.

## 10. 문제를 해결할 때 팀이 판단한 방식

처음부터 실제 운영 시스템 전체를 만들기보다 MVP 범위를 줄였다.

핵심 기능은 request_id, trace_id, 비용, 토큰, latency, 단계별 병목, 알림으로 좁혔다. 복잡한 기능은 빼고, 실제 운영에서 발생할 법한 상황은 mock/demo 시나리오로 재현했다.

또한 당장 완성하기 어려운 부분은 무리하게 구현하기보다 문서에 한계와 추후 확장 방향으로 정리했다.

## 11. AI가 대신한 것이 아니라 팀이 방향을 잡은 부분

첫째, 프로젝트의 핵심을 단순 LLM 챗봇 개발이 아니라 LLM 운영 관측성으로 잡은 부분이다.

둘째, 외부 API 대신 로컬 SLM을 선택해 비용과 시연 안정성 문제를 줄인 부분이다.

셋째, 로그인이나 복잡한 권한 기능보다 request_id, trace_id, 비용, latency, 병목 분석에 집중하기로 한 부분이다.

이 부분들은 AI가 자동으로 결정한 것이 아니라, 팀이 발표 목표와 프로젝트 범위를 고려해 선택한 방향이다.

## 12. 최종 발표에서 어필하고 싶은 한 문장

> OLLY는 LLM 답변 품질 평가기가 아니라, LLM 서비스 운영자가 비용, 지연, 토큰 사용량, 실패 원인을 request_id와 trace_id로 추적하게 해주는 관측성 플랫폼입니다.
