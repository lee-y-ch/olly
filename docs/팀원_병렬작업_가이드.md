# 팀원 4명 병렬 작업 가이드

이 문서는 팀원 4명이 서로 충돌을 줄이면서 동시에 작업하기 위한 분업 계획이다.

현재 OLLY는 이미 MVP가 동작한다. 따라서 앞으로의 작업은 **기존 MVP를 깨지 않고 발표 완성도와 기능 완성도를 높이는 방향**으로 진행한다.

## 1. 공통 약속

아래 이름은 바꾸지 않는다.

| 항목 | 값 |
| --- | --- |
| 사용자 화면 | `http://localhost:8001/chat-ui` |
| 운영자 화면 | `http://localhost:8001/dashboard` |
| API 문서 | `http://localhost:8001/docs` |
| 질문 API | `POST /chat` |
| 로컬 모델 | `gemma3:1b` |
| LLM 백엔드 | `ollama` |
| trace 단계 | `retrieve`, `llm_call`, `postprocess` |
| API 서비스 이름 | `olly-sample-api` |
| API 로컬 포트 | `8001` |
| Grafana 로컬 포트 | `3001` |
| Prometheus 로컬 포트 | `9090` |
| Jaeger 로컬 포트 | `16686` |

공통 브랜치 전략:

```text
main
  ├─ feature/api-observability
  ├─ feature/frontend-demo
  ├─ feature/dashboard-alerts
  └─ feature/docs-presentation
```

작업 전:

```bash
git pull origin main
```

작업 후:

```bash
docker compose -f deploy/docker-compose.yml up -d --build
```

최소 확인:

```text
/chat-ui에서 질문 전송 가능
/dashboard에서 최근 요청 확인 가능
```

## 2. 1번 팀원: API / LLM 처리 담당

### 책임

`POST /chat`의 동작을 안정화하고, 로컬 LLM 호출과 응답 구조를 관리한다.

### 담당 파일

```text
apps/sample-llm-api/app/main.py
apps/sample-llm-api/app/schemas.py
apps/sample-llm-api/app/ollama_llm.py
apps/sample-llm-api/app/mock_llm.py
apps/sample-llm-api/app/pricing.py
apps/sample-llm-api/app/config.py
```

### 해야 할 일

- `/chat` 응답 구조 유지 및 개선
- `normal`, `slow_retrieve`, `slow_llm`, `high_token`, `error` 시나리오 안정화
- Ollama 응답 실패 시 에러 메시지 개선
- 토큰 계산 방식 개선
- 로컬 비용 계산 방식 주석/문서화
- 모델 변경 가능성 정리

### 완료 기준

- 모든 scenario가 정상 재현된다.
- 응답에 아래 필드가 항상 포함된다.

```text
request_id
trace_id
answer
model
feature
llm_backend
input_tokens
output_tokens
cost_usd
token_cost_usd
infra_cost_usd
compute_seconds
latency_ms
status
```

### 다른 팀원과 맞출 것

- field 이름을 바꾸면 2번, 3번, 4번 팀원에게 공유한다.
- scenario 이름을 바꾸지 않는다.
- `retrieve`, `llm_call`, `postprocess` 단계 이름을 바꾸지 않는다.

## 3. 2번 팀원: 관측성 / OpenTelemetry / Metric 담당

### 책임

API 내부에서 발생한 요청 정보를 trace와 metric으로 남긴다.

### 담당 파일

```text
apps/sample-llm-api/app/telemetry.py
apps/sample-llm-api/app/metrics.py
apps/sample-llm-api/app/main.py
observability/otel-collector.yaml
observability/prometheus.yml
```

### 해야 할 일

- `retrieve`, `llm_call`, `postprocess` span 속성 정리
- `request_id`, `trace_id`, `feature`, `scenario`, `model`이 trace에 남는지 확인
- Prometheus metric 이름과 label 정리
- 고카디널리티 label 위험성 정리
- `/metrics`가 Prometheus에서 scrape되는지 확인
- Jaeger에서 `POST /chat` trace가 잘 보이는지 확인

### 중요 metric

```text
olly_requests_total
olly_tokens_total
olly_cost_usd_total
olly_token_cost_usd_total
olly_infra_cost_usd_total
olly_inference_compute_seconds_total
olly_request_duration_seconds
olly_stage_duration_seconds
olly_llm_duration_seconds
olly_generation_tokens_per_second
olly_errors_total
```

### 완료 기준

- `/chat-ui`에서 질문을 보내면 Jaeger에 trace가 생긴다.
- Prometheus에서 주요 metric이 조회된다.
- slow scenario에서 해당 span 시간이 길게 보인다.
- error scenario에서 error metric이 증가한다.

### 다른 팀원과 맞출 것

- 3번 팀원이 대시보드 쿼리를 만들 수 있게 metric 이름을 공유한다.
- 1번 팀원의 API 구조 변경이 span/metric에 반영되는지 확인한다.

## 4. 3번 팀원: 프론트엔드 / 운영자 대시보드 담당

### 책임

사용자 챗봇 화면과 운영자 대시보드 화면을 발표에 맞게 개선한다.

### 담당 파일

```text
apps/sample-llm-api/app/dashboard.py
apps/sample-llm-api/app/static/chat_ui.html
apps/sample-llm-api/app/static/dashboard.html
```

### 해야 할 일

- `/chat-ui` 사용성 개선
- 시나리오 선택 UI 개선
- 응답 metadata 표시 개선
- `/dashboard` Recent Requests 테이블 개선
- Trace Detail waterfall 가독성 개선
- `Open in Jaeger` 링크 동작 확인
- 화면이 작은 발표 환경에서도 깨지지 않도록 반응형 보완
- 필요하면 `/api/dashboard/summary` 응답 구조 개선

### 완료 기준

- `/chat-ui`에서 질문 전송이 된다.
- 질문 결과 metadata가 보인다.
- `/dashboard`에서 방금 요청이 보인다.
- 요청 클릭 시 단계별 병목이 보인다.
- 브라우저 console error가 없다.

### 다른 팀원과 맞출 것

- 1번 팀원의 `/chat` 응답 필드를 그대로 사용한다.
- 2번 팀원의 metric/trace 구조를 대시보드에 반영한다.
- 4번 팀원에게 발표용 화면 순서를 공유한다.

## 5. 4번 팀원: 문서 / 발표 / 실행 검증 담당

### 책임

팀원이 같은 방식으로 실행하고 발표할 수 있도록 문서와 데모 흐름을 정리한다.

### 담당 파일

```text
README.md
docs/OLLY_쉬운_이해_가이드.md
docs/MVP_진행계획.md
docs/demo_scenario.md
docs/local_gemma3_setup.md
docs/대시보드_사전검증_결과.md
docs/팀원_병렬작업_가이드.md
```

### 해야 할 일

- 실행 방법 최신화
- 화면별 역할 설명 정리
- 발표 흐름 정리
- 팀원별 작업 범위 정리
- 자주 나는 문제 정리
- 발표 대본 초안 작성
- 최종 데모 체크리스트 작성

### 완료 기준

- 새 팀원이 문서만 보고 실행할 수 있다.
- 발표자가 문서만 보고 데모 순서를 따라 할 수 있다.
- `/chat-ui`, `/dashboard`, `/docs`, Jaeger, Prometheus, Grafana 역할이 명확하다.
- 팀원별 담당 파일과 완료 기준이 명확하다.

### 다른 팀원과 맞출 것

- 1번 팀원에게 API 응답 필드를 확인한다.
- 2번 팀원에게 metric/trace 이름을 확인한다.
- 3번 팀원에게 실제 화면명과 버튼명을 확인한다.

## 6. 병렬 작업 순서

각자 동시에 시작하되, 아래 체크포인트에서만 맞추면 된다.

### 체크포인트 1: 공통 실행 확인

모든 팀원이 아래 명령을 성공시킨다.

```bash
docker compose -f deploy/docker-compose.yml up -d --build
```

확인:

```text
http://localhost:8001/chat-ui
http://localhost:8001/dashboard
```

### 체크포인트 2: API 계약 확인

1번 팀원이 `/chat` 응답 예시를 공유한다.

나머지 팀원은 해당 필드 기준으로 작업한다.

### 체크포인트 3: 관측 데이터 확인

2번 팀원이 Jaeger trace와 Prometheus metric이 찍히는지 공유한다.

3번 팀원은 그 데이터를 대시보드에 연결한다.

### 체크포인트 4: 발표 리허설

4번 팀원이 발표 순서대로 진행한다.

확인할 시나리오:

```text
Normal Request
Slow Retrieval (RAG)
Slow LLM Response
High Token Usage
Error Occurred
```

## 7. 최종 통합 체크리스트

- `/chat-ui`에서 질문 전송 가능
- `/chat-ui`에서 latency, tokens, cost, trace_id 표시
- `/dashboard`에서 Recent Requests 표시
- 요청 클릭 시 Trace Detail 표시
- Slow Retrieval에서 Retrieve 병목 표시
- Slow LLM에서 LLM Generation 병목 표시
- High Token Usage에서 토큰/비용 증가
- Error Occurred에서 ERROR 요청 표시
- Jaeger에서 `POST /chat` trace 확인
- Prometheus에서 `olly_requests_total` 조회
- 문서의 실행 명령이 실제로 동작
